SECTION 1: HIGH-LEVEL PROJECT OVERVIEW
================================================================================

WHAT THE PROJECT DOES:
---------------------
AgroVision is an AI-powered agricultural market intelligence platform that provides 
real-time crop prices, price predictions, market analysis, and an intelligent chatbot 
for farmers, merchants, and retail customers in India.

WHO IT'S FOR:
-------------
1. FARMERS - Need to know when to sell their crops at the best price, understand 
   weather impacts on their specific crops, and get actionable recommendations.
   
2. MERCHANTS/TRADERS - Need to identify buying opportunities, track market volatility, 
   understand supply chain factors, and find arbitrage opportunities.
   
3. RETAIL CUSTOMERS - Need to understand retail pricing (converted from wholesale), 
   seasonal availability, and when to make bulk purchases.

REAL-WORLD PROBLEM SOLVED:
--------------------------
India's agricultural market is highly fragmented with information asymmetry. Farmers 
often sell at unfavorable prices due to lack of real-time market data. This platform 
democratizes access to:

1. Real-time pricing data across regions
2. Weather-based crop impact analysis (critical for farming decisions)
3. AI-powered price predictions to time market entry/exit
4. Market factor analysis (policy changes, demand/supply dynamics)
5. Multilingual support (11 Indian languages) for accessibility

The platform essentially acts as a "Bloomberg Terminal for Indian Agriculture" - making 
professional-grade market intelligence accessible to everyday farmers.

DATABASE SCHEMA (PostgreSQL via Supabase):
------------------------------------------
TABLES:
1. crops
   - id (UUID, PRIMARY KEY, auto-generated)

4. news
   - id (UUID, PRIMARY KEY)

   - url (TEXT)
   - image_url (TEXT)
   - source (TEXT)
   - published_date (TIMESTAMP WITH TIME ZONE)

SECTION 3: END-TO-END FEATURE WALKTHROUGH
================================================================================

FEATURE: User Views Crop Detail Page and Gets Price Prediction

STEP 1: USER ACTION
User clicks on "Wheat" card on dashboard

STEP 2: FRONTEND ROUTING
- React Router catches /crop/:id route
- CropDetail component mounts
- useParams() extracts crop ID from URL

STEP 3: PARALLEL API CALLS
CropDetail.jsx makes 5 simultaneous requests via Promise.all():
  - fetchCropDetails(id)     → /api/crops/:id
  - fetchPriceHistory(id)    → /api/crops/:id/prices
  - fetchPrediction(id)      → /api/crops/:id/prediction
  - fetchFactors(id)         → /api/crops/:id/factors
  - fetchNews(id)            → /api/crops/:id/news

STEP 4: BACKEND - Crop Details
Route: GET /api/crops/:id
Flow:
  1. UUID validation (regex check)
  2. Crop.getById(id) calls Supabase
  3. Supabase query: SELECT * FROM crops WHERE id = :id
  4. Returns crop object with current price, category, etc.

STEP 5: BACKEND - Price Prediction Algorithm
Route: GET /api/crops/:id/prediction
Flow:
  1. Fetch last 30 price history records from Supabase
  2. Calculate Simple Moving Average (SMA):
     - avgRecent = average of days 0-6
     - avgOlder = average of days 7-13
  3. Calculate trend: (avgRecent - avgOlder) / avgOlder
  4. Apply prediction formula:
     - next3Days = currentPrice × (1 + trend × (3/7) + randomFactor)
     - nextMonth = currentPrice × (1 + trend × 2 + randomFactor × 1.5)
  5. Calculate confidence: min(95, 60 + (dataPoints/30) × 35)
  6. Return: { next3Days, nextMonth, confidence, trend }

STEP 6: BACKEND - Crop-Specific Factors
Route: GET /api/crops/:id/factors
Flow:
  1. Fetch crop name from Crop.getById()
  2. Get current weather from weatherService
  3. Use cropSensitivities.js to calculate impact:
     - Each crop has sensitivity profiles (rain, drought, heat, etc.)
     - Weather impact calculated: temp impact + rain impact + humidity impact
  4. Adjust base factor scores using crop multipliers
  5. Return enhanced factors with crop_specific_impact field

STEP 7: RESPONSE AGGREGATION
All 5 API responses return to frontend simultaneously

STEP 8: STATE UPDATE
CropDetail component updates state:
  - setCrop(cropData)
  - setPriceHistory(historyData)
  - setPrediction(predictionData)
  - setFactors(factorsData)
  - setNews(newsData)

STEP 9: ROLE-BASED PRICE TRANSFORMATION
If user role is 'customer':
  - Convert quintal prices to kg: price / 100
  - Add 20% retail markup: price × 1.20
  - Update unit display: 'QUINTAL' → 'KG'

STEP 10: UI RENDERING
Components render:
  - MetricCard with current price + trend arrow
  - PriceChart with historical line (green) + prediction line (orange dashed)
  - PredictionCard with confidence indicator
  - FactorsList with crop-specific impacts
  - News cards with external links

SECTION 5: SCALABILITY, RELIABILITY & PERFORMANCE CONCERNS
================================================================================

CURRENT LIMITATIONS & SOLUTIONS:

1. DATABASE QUERY OPTIMIZATION
   PROBLEM: No indexes defined in schema; queries will slow at scale
   SOLUTION:
   - Add indexes: CREATE INDEX idx_price_history_crop_date ON price_history(crop_id, date DESC);
   - Add index: CREATE INDEX idx_factors_crop ON factors(crop_id);
   - Consider materialized views for dashboard aggregations

2. RATE LIMITING IS TOO SIMPLE
   PROBLEM: 100 requests/15min per IP doesn't handle:
   - Authenticated users needing higher limits
   - API key-based rate limiting for B2B
   SOLUTION:
   - Implement tiered rate limiting
   - Add Redis for distributed rate limiting across multiple servers
   - Token bucket algorithm for smoother request handling

3. NO CACHING LAYER
   PROBLEM: Every request hits database/external APIs
   SOLUTION:
   - Redis cache for crop data (5-min TTL)
   - Weather data cache (15-min TTL)
   - News cache (1-hour TTL)
   - CDN for static assets

4. PREDICTION ALGORITHM IS SIMPLISTIC
   PROBLEM: Simple moving average won't handle:
   - Seasonal patterns
   - Market shocks
   - Policy announcements
   SOLUTION:
   - Implement ARIMA or Prophet for time series forecasting
   - Add external factors (commodity index, fuel prices) as features
   - ML pipeline with feature engineering

5. SINGLE REGION WEATHER
   PROBLEM: Default location is Delhi; India has diverse climate zones
   SOLUTION:
   - User location detection via browser geolocation API
   - Allow farmers to set their specific taluka/district
   - Aggregate weather data from multiple stations

6. NO WEBSOCKET FOR REAL-TIME UPDATES
   PROBLEM: Users must refresh to see new prices
   SOLUTION:
   - Supabase real-time subscriptions are already available
   - Implement WebSocket connection for price ticker
   - Push notifications for price alerts

7. ERROR HANDLING IN CHATBOT
   PROBLEM: If OpenAI API is down, user gets generic error
   SOLUTION:
   - Implement circuit breaker pattern
   - Queue requests during outage
   - Provide FAQs/cached responses as fallback

8. NO HORIZONTAL SCALING STRATEGY
   PROBLEM: Single Express server is a bottleneck
   SOLUTION:
   - Containerize with Docker
   - Deploy on Kubernetes with auto-scaling
   - Stateless design already supports multiple instances
   - Add load balancer (already supported via Vercel)

SECTION 6: DESIGN TRADE-OFFS
================================================================================

TRADE-OFF 1: Context API vs Redux
CHOSE: React Context API
WHY: Simpler for role/theme state; no complex state mutations needed
ALTERNATIVE: Redux Toolkit would be better if:
  - Needed time-travel debugging
  - Had complex async flows
  - Multiple components needed same derived state
INTERVIEW DEFENSE: "Given the scope of state management needed (just role and 
settings), Context API provides sufficient capability without the boilerplate 
of Redux. If we added features like shopping cart or order management, I'd 
refactor to Redux Toolkit."

TRADE-OFF 2: Client-Side Filtering vs Server-Side
CHOSE: Fetch all crops, filter locally
WHY: Small dataset (~12 crops); instant search feedback
ALTERNATIVE: Server-side would be better with:
  - Thousands of crops
  - Complex filter combinations
  - Pagination requirements
INTERVIEW DEFENSE: "With 12 crops, the network overhead of repeated searches 
outweighs the benefits. The entire dataset is ~5KB. I'd refactor to server-side 
search at ~100+ items."

TRADE-OFF 3: Supabase vs Self-Managed PostgreSQL
CHOSE: Supabase (managed Postgres)
WHY: Quick setup, built-in real-time, auth ready
ALTERNATIVE: Self-managed would be better for:
  - Cost optimization at scale
  - Custom extensions
  - Data residency requirements
INTERVIEW DEFENSE: "Supabase accelerated development with zero DevOps overhead. 
For production at scale, I'd evaluate cost-benefit of migrating to RDS or 
self-managed Postgres."

TRADE-OFF 4: Simulated Data vs Real Market Integration
CHOSE: Simulated price generation when no DB data
WHY: Demonstrates functionality without paid data feeds
ALTERNATIVE: Integrate with actual market APIs (AGMARKNET, commodity exchanges)
INTERVIEW DEFENSE: "Real-time market data APIs in India are expensive or 
require partnerships. The simulation demonstrates the architecture; swapping 
to real APIs is a configuration change, not an architectural one."

TRADE-OFF 5: No Authentication/Authorization
CHOSE: Role selection without login
WHY: Demo purposes; showcases role-based features
ALTERNATIVE: Full auth with Supabase Auth + RLS policies
INTERVIEW DEFENSE: "Auth scaffolding exists (Supabase SDK imported, AuthContext 
ready). Production would add email/phone auth, farmer KYC, and row-level 
security for personal data."

TRADE-OFF 6: Hardcoded Fallback Data in Chatbot
CHOSE: Fallback crop prices if database query fails
WHY: Better UX than error message
ALTERNATIVE: Could return partial data or cache last known state
INTERVIEW DEFENSE: "Graceful degradation prioritizes user experience. The 
fallback data is marked in the AI context so the bot can indicate 'using 
reference prices' if needed."

A. LIBRARY/FRAMEWORK CHOICES

REACT vs Vue/Angular:
"React's component model and hooks align well with the data dashboard pattern. 
The ecosystem (Recharts, Framer Motion) is more mature for data visualization."

TAILWIND vs CSS/Styled-Components:
"Tailwind provides design consistency through constrained utilities and eliminates 
CSS bloat. Co-located styles in JSX improve developer velocity without sacrificing 
customization."

EXPRESS vs Fastify/NestJS:
"Express's middleware ecosystem (Helmet, rate-limiter) and mature documentation 
made it the pragmatic choice. For a TypeScript-heavy team, I'd consider NestJS."

SUPABASE vs Firebase/Raw Postgres:
"Supabase gives PostgreSQL power (joins, transactions) with Firebase-like DX. 
Real-time subscriptions are built-in, making future live updates trivial."

RECHARTS vs D3/Chart.js:
"Recharts is React-native with declarative APIs. D3 offers more control but 
requires imperative DOM manipulation. Chart.js lacks React integration depth."

SECTION 9: INTERVIEW-READY ANSWERS
================================================================================

A1. DATA FLOW FOR WHEAT DETAIL PAGE
"When a farmer clicks on Wheat, React Router captures the crop ID from the URL. 
The CropDetail component mounts and fires five parallel API requests using 
Promise.all - for crop details, price history, predictions, market factors, and 
news. Each request goes through axios interceptors that log the call, then hits 
Express routes that validate the UUID format. The crop model queries Supabase 
with the ID. For predictions, we fetch the last 30 price points, calculate a 
7-day moving average trend, and extrapolate forward. The factors endpoint 
cross-references current weather conditions against our crop sensitivity profiles 
to generate wheat-specific impact scores. Everything returns simultaneously, 
and since the farmer role is in context, prices display as wholesale in Quintals."

A2. CROP SENSITIVITY ENGINE
"It's a configuration object where each crop has quantified sensitivity values 
from -1 to +1 for factors like rain, drought, heat, and humidity. I chose static 
configuration over a database table for three reasons: one, these sensitivities 
rarely change - rice always needs water; two, it's domain knowledge that 
agricultural scientists would review via code PR, not admin panels; three, it 
gives O(1) lookup with no database round-trip. The trade-off is harder updates 
for non-developers, which I'd solve with a config management UI if needed."

A3. CHATBOT CONTEXT AWARENESS
"Every chatbot request includes a context object with the current page path, 
user role, and language. In the backend, I parse the path - if it's /crop/:id, 
I extract the ID, fetch that crop, and inject an 'Active Crop Context' block 
into the AI prompt that explicitly says 'User is viewing Wheat. If they ask 
about price without specifying a crop, refer to Wheat.' On the dashboard, no 
active crop exists, so the AI falls back to asking which crop they mean. This 
is essentially retrieval-augmented generation with runtime context injection."

A4. PRICE PREDICTION LIMITATIONS
"The current SMA approach has three major limitations: it's purely 
autoregressive with no exogenous factors like monsoon forecasts or MSP 
announcements; it doesn't capture seasonality since crops have annual cycles; 
and it assumes linear trends which fail during market shocks. For production, 
I'd implement Facebook Prophet which handles seasonality and holidays, or a 
gradient-boosted model with features like fuel prices, rainfall deviation, 
and government policy sentiment scores. I'd also add backtesting to validate 
MAPE before deployment."

A5. SCALING TO 100K CONCURRENT USERS
"Three layers: First, horizontally scale Express with Kubernetes pods behind 
a load balancer - the app is already stateless. Second, add Redis caching - 
crop data refreshes every 5 minutes so we'd cache at 4-minute TTL; price 
history by crop ID for 1 minute. Third, offload heavy computations - the 
prediction algorithm would move to a separate worker service with a queue. 
Database-wise, I'd add read replicas for Supabase or move to RDS with pgpool 
for connection pooling. CDN for static assets is already on Vercel."

A6. ROLE-BASED PRICING IMPLEMENTATION
"Transformation happens at two points. In the frontend, CropDetail component 
reads role from AuthContext, then applies the formula if role is 'customer': 
divide by 100 to convert quintal to kg, multiply by 1.20 for retail markup. 
The same logic exists in the chatbot backend - when building the crop context 
string, it maps over the merged crop list and transforms prices based on the 
sanitized role from the request body. This keeps the database clean with 
wholesale prices while presenting role-appropriate data."

A7. WEATHERAPI FAILURE HANDLING
"The weatherService has a try-catch that throws on API failure. In routes 
like /factors, we wrap the weather call in its own try-catch and set 
currentWeather to null if it fails. The factor generation logic checks if 
currentWeather exists - if not, it returns a placeholder factor with 'Weather 
data unavailable' and zero impact score. In the chatbot, similar fallback: 
the weather context section says 'Weather data temporarily unavailable' 
instead of crashing. This pattern is graceful degradation - partial 
functionality beats a hard error."

A8. CONTEXT API VS REDUX
"I chose Context for two reasons: one, the state shape is simple - just role 
string and theme/language settings; two, there are no complex async actions 
or derived state calculations that benefit from Redux middleware. I'd refactor 
when we add shopping cart (optimistic updates), price alerts (complex async), 
or multi-step order flows (needs undo/redo). At that point, Redux Toolkit with 
RTK Query for data fetching would replace both Context and raw axios calls."

A9. REAL-TIME PRICE UPDATES
"Supabase SDK is already imported and configured. I'd add a useEffect in the 
Dashboard that subscribes to the crops table: supabase.channel('prices')
.on('postgres_changes', { event: 'UPDATE', schema: 'public', table: 'crops' }, 
callback).subscribe(). The callback would update the local crops state. For 
scale, I'd add a price_updates table with timestamps, subscribe only to that, 
then fetch full crop data on change. This reduces payload size for high-
frequency updates."

A10. RATE LIMITING FOR B2B API
"Current implementation is IP-based with fixed limits. For B2B, I'd add API 
key authentication, store keys in Redis with metadata including tier (free/
basic/enterprise) and rate limits. The rate limiter would extract the key 
from headers, look up the limit, and apply token bucket algorithm per key 
instead of per IP. I'd also add usage tracking for billing, abuse detection 
for automated throttling, and webhook notifications approaching limits."

A11. NEWS CACHING STRATEGY
"The endpoint first checks DB for news updated within 24 hours. If fresh, 
return it. If stale or empty, call NewsAPI, save results, return them. 
Potential issues: one, thundering herd - multiple users request simultaneously, 
all call API. Solution: distributed lock with Redis SETNX. Two, partial 
failure - API returns but DB insert fails. Solution: still return the data, 
log the insert failure. Three, stale cache during breaking news. Solution: 
webhook from content team to invalidate, or reduce TTL with background refresh."

A12. DEBUGGING INCORRECT PRICES
"I'd start with reproduction - get the user's role, crop ID, and timestamp. 
Check if the issue is role-transformation: verify AuthContext role vs what 
they expect. Then trace the API: check /crops/:id response raw values against 
database. If DB is correct but frontend is wrong, check for JS floating point 
issues or caching. If DB is wrong, check the last updatePrices job run. I'd 
add request logging with user ID, role, and crop ID to make this faster 
in production. Sentry would capture the frontend state at error time."

A13. GDPR COMPLIANCE CHANGES
"First, no user data is currently stored, which helps. With user accounts, 
I'd add: one, consent management - explicit opt-in for data collection with 
version-tracked consent records. Two, data export API - let users download 
their search history, favorites, etc. Three, right to deletion - soft delete 
with 30-day purge job. Four, data encryption at rest using Supabase's built-in 
column encryption. Five, audit logging for all data access. Six, update privacy 
policy with clear retention periods. Seven, DPA with Supabase and other processors."

A14. HANDLING EMPTY PRICE HISTORY
"The /prices endpoint checks data.length after the Supabase query. If zero, 
it falls back to generation: fetch the crop's current_price, set a starting 
price at 90% of current, then loop 90 days with random walk adding daily 
changes with slight upward bias. This returns synthetic but realistic data. 
The chart renders normally. There's a comment in the API marking this as 
demo behavior - production would surface a 'Limited data' indicator to users."

A15. SUPABASE TO SELF-MANAGED MIGRATION
"Supabase uses standard PostgreSQL, so schema migration is straightforward: 
pg_dump the database, restore to RDS/Cloud SQL/self-hosted. Connection string 
change in environment variables. The Supabase SDK calls are thin wrappers 
around Postgres queries, but I'd swap to Prisma or raw pg library for tighter 
control. Real-time subscriptions would need rebuild - either Postgres LISTEN/
NOTIFY with application-side WebSocket broadcast, or a dedicated service like 
Pusher. Auth would move to Auth0 or Cognito. Migration plan: parallel run both 
databases, verify data parity, gradual traffic shift."

SECTION 12: HONEST WEAKNESS ACKNOWLEDGMENT
================================================================================

WEAKNESSES AND DEFENSES:

1. NO REAL MARKET DATA
   "This uses simulated prices, not live market feeds."
   DEFENSE: "The architecture abstracts data fetching - swapping to AGMARKNET 
   or commodity exchange APIs is a configuration change. The simulation 
   demonstrates the visualization and analysis capabilities."

2. NO AUTHENTICATION
   "Anyone can switch roles; there's no real user management."
   DEFENSE: "Supabase Auth is ready to integrate. This demo prioritizes 
   showing role-based features over login flows. Production would add 
   phone OTP auth (common in rural India) with Plivo's SMS API."

3. SIMPLE PREDICTION MODEL
   "Moving average isn't scientific forecasting."
   DEFENSE: "Intentionally simple to demonstrate the concept without 
   overfitting. Production would use ML models trained on historical data 
   with proper validation. The frontend already handles confidence scores 
   to show uncertainty."

4. SINGLE LANGUAGE CODEBASE
   "No TypeScript means fewer compile-time safety checks."
   DEFENSE: "Rapid prototyping trade-off. For a production system I'd add 
   TypeScript for API contracts and prop types. JSDoc comments partially 
   compensate."

5. LIMITED TEST COVERAGE
   "Playwright tests exist but coverage isn't comprehensive."
   DEFENSE: "I prioritized e2e tests for critical user journeys over unit 
   tests for utility functions. Production would add API integration tests, 
   component tests with Testing Library, and contract tests for external APIs."

6. MONOLITHIC BACKEND
   "Single Express app handles everything."
   DEFENSE: "Appropriate for current scale. If weather service gets heavy 
   traffic, I'd extract it to a microservice. The code is already modular 
   enough (routes/, services/, models/) to split cleanly."
